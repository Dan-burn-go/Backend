# 013. 분산락 값에 소유 토큰을 넣고, 해제는 Lua 로 내 토큰일 때만 지운다

- 날짜: 2026-10-16
- 상태: 채택

## 배경
004 의 락은 값 `"1"` 로 `SET NX EX` 하고 실패 시 무조건 `DEL` 했다. 처리가 TTL(300초)을 넘기면 락이 만료되고, 재전달된 같은 이벤트를 다른 소비자가 잡는다. 그 뒤 먼저 잡았던 쪽이 실패해 `DEL` 하면 남의 락을 지우고, 이후 중복 이벤트가 다시 LLM 을 호출한다.

## 결정
- `acquire` 는 선점마다 `uuid4` 토큰을 값으로 넣고 토큰을 돌려준다 (실패 시 `None`)
- `release(key, token)` 은 Lua `if get(key) == token then del(key)` 로 확인과 삭제를 원자적으로 한다
- `BatchProcessor` 는 fresh 항목과 같은 순서로 토큰을 들고 있다가 실패 시 자기 토큰으로 해제한다
- Redis 장애 시 fail-open 은 그대로다. 토큰을 돌려주고 해제는 실패를 무시한다

## 근거
- 테스트 (`service-ai/tests/test_dedup.py`):
  - A 처리 중 TTL 만료 → B 선점·성공 → A 실패 해제 → 이후 중복 10건. Before: LLM 호출 2건 (A 가 B 의 마커를 지워 재호출). After: 1건
  - 같은 이벤트 20건(배치 안 중복 5 + 재전달 15) → LLM 호출 1건
- 실제 Redis 7 로 확인: TTL 1초로 줄여 실제 만료 후 B 선점, A 해제 뒤에도 값이 B 토큰 그대로. 기존 `DEL` 은 B 의 락을 지움
- `GET` 후 `DEL` 을 따로 보내면 그 사이에 만료·재선점이 끼어들 수 있어 Lua 로 묶었다
- 버린 대안
  - 프로세스 안 dict 로 key → token 보관: 같은 프로세스의 normal·anomaly 처리기가 같은 키를 TTL 뒤 다시 잡으면 덮어써서 같은 문제가 남는다. 호출마다 토큰을 들고 다니게 했다
  - 2키 패턴 (처리 중 락 + 완료 마커 분리): 크래시 구간까지 닫지만 키 두 개의 상태 전이를 관리해야 한다. 지금 한계 구간은 DB UNIQUE(005)가 저장 중복을 막아 토큰 낭비 문제만 남는다
  - 인박스 패턴 (소비 기록을 DB 에 남겨 멱등 판정): 강한 보장이지만 service-ai 는 DB 에 쓰지 않는다는 원칙(ARCHITECTURE)과 충돌한다
  - Redisson 등 락 라이브러리 / watchdog 연장: Python 쪽이라 해당 없고, 재시도 예산(≤105초)이 TTL 보다 짧아 연장이 필요 없다

## 결과/영향
- 남은 한계 1: 락을 잡은 뒤 해제 전에 프로세스가 죽으면 마커가 TTL 까지 남아, 그동안 재전달·DLQ 재처리가 스킵된다. 저장은 안 됐을 수 있다. 2키 패턴이 필요해지면 다시 본다
- 남은 한계 2: 처리가 TTL 을 넘기면 중복 LLM 호출 자체는 여전히 생길 수 있다(A·B 둘 다 호출). 토큰 해제는 그 뒤 추가 중복을 막을 뿐이다. TTL > 재시도 예산을 유지해야 한다
- Lua 는 Redis 단일 노드 기준이다. 클러스터로 가도 키 하나라 그대로 동작한다
